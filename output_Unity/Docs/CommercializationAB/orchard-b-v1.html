本轮交付设计及待实施参数，不修改当前游戏流程、不接入实验路由、不打包。A 为当前已接入的现金与钻石方案；B 为独立新方案。这里的“两套”用于后续 A/B 测试，不是两天流程。

参考已读取的仓库提交 df1d9c1；苹果树基线 e2b98d8，另有既存未提交改动，本轮不纳入 A 的冻结版本。下列 B 数值均为设计建议，不冒称参考实装或已验证收益。

1. 参考项目究竟提供了什么

代码有五套框架。包内兜底配置为 F4/F5 各 50%，远端可覆盖。B 主要借鉴 F5 的“五关汇总—生成记录—任务推进”，辅以 F4 的幸运奖励节奏及 F1 的广告保护。旧商业化文档与部分当前参数不一致，以代码和配置为依据。

参考机制B 的苹果树适配
F5 每显示5关汇总一次，短反馈与长记录分层每5个真实通关合成一次丰收汇总；只弹一个关卡结算，汇总是其内的状态。
F5 时长、等待、后续关卡、等级条件链精简为申请后10关、20分钟有效玩法、48小时；全部提前显示、并行累计，省去缺少增长入口的账户等级。
F4 幸运奖励按消除数或时间出现8组三消且45秒后出现可点果篮入口；不打断水果选择，末组三消不触发。
F1/F4 的广告机会和保护普通领奖计次产生机会；统一冷却与新手保护。奖励视频由玩家主动选择。
框架分组固化、业务数据分域A/B 各自的 Prefab、配置、账本、引导和订单；同一玩法事件只给当前组。

参考 F5 的“全部条件完成”与支付成功不是同一回事；结果页还存在条件完成分支未闭环的问题。B 明确定义有限的 SimulatedCompleted，保留测试状态，完成不表示真实现金到账。参考中显示额与记账额不同、逐项才揭露条件、模拟他人到账等做法，不纳入 B。

2. A 与 B 的核心区别

维度A：现有流程，原样保留B：果园丰收单
主要节奏前两笔奖励记录→激活→现金/钻石任务每5关丰收汇总→自主提交→完整任务清单→测试完成
钱包入口现金、钻石分别进入现有页面现金进入收获单；钻石进入每日任务及固定兑换
短期反馈现有三消、幸运奖、通关奖和10倍测试视频单关基础奖＋5关额外奖；自愿3倍，倍率固定
长期目标现有关卡、登录日、账户等级条件明确的10关、20分钟、48小时；建单后不变
存档原 fruit-apk-earning-v1.dat新 fruit-orchard-earning-b-v1.dat，不导入A余额
视觉已完成的苹果树立体风格共享同风格的基础美术，页面结构和流程独立
A 基线事实：当前广告为本地测试视频；CashTargetCents 与 AccountLevel 没有正常生产更新入口，后段也没有通用真实支付终点。因此早期 A/B 可比玩法、入口与领取行为，不能把“真实到账率”或模拟视频收入当指标。A 不在本设计中被偷偷修成另一套。

3. B 的玩家完整路径

直接进入关卡 → 采果与通关积累 → 每5关丰收汇总 → 查看完整收获单 → 确认申请并冻结 → 三项任务并行 → 确认测试完成 → 历史记录
阶段玩家看到什么行为及数据
首次进入沿用顶部一行：等级、现金、钻石、设置不恢复旧开始页，不先弹钱包；用一次轻量提示介绍测试奖励。
第1～4关单一结算页；本关奖励、普通领取、可选3倍基础奖固定，先保证玩法闭环。第1～2关不出广告，第3关起才提供可选加奖。
第5关及以后每5关同一个结算页切到丰收汇总状态显示本周期基础、额外奖励、加奖明细；查看收获单或继续游戏，不强制申请。
申请前本次金额、全部三项要求、冻结说明、测试标识不要求真实银行卡或支付账号；演示账户足够，关闭不扣款。
确认申请一笔进行中的收获单同一事务扣可用、加冻结、保存条件快照和起点；写入成功才显示申请成立。
任务进行三个进度同时可见新通关10关；有效玩法20分钟；申请起48小时。任一完成后不会出现新门槛。
全部完成按钮变为“完成测试订单”点击后消耗该笔冻结额，记为测试完成，不发起现金支付。
取消/继续取消可在任务中或待确认时使用取消原额退还，完成与退款互斥；下次申请重新计时、计任务。

同一时间仅一笔活跃单。活跃单期间继续发通关和五关奖励，新奖励留在可用余额；新申请入口说明“先完成或取消当前订单”。每次汇总均不吞奖，也不自动再冻结一笔。

幸运果篮8组三消且有效玩法45秒；基础2测试现金每个唯一实际关卡至多1次、每天至多10次；末组不触发，未领本局果篮随结算普通领取。
自愿加奖普通通关或幸运基础奖×3不乘五关额外奖、签到、任务、兑换；页面明确显示基础和新增部分。

任务门槛申请后10个新通关＋1200有效秒＋172800秒等待三者并行；任务与金额、倍率都随建单快照固定。

有效时间按1:1计入：前台、玩法可操作、最近15秒有接受的水果选择或有效玩法操作；广告、弹窗、暂停、后台和超过15秒的空闲不计。48小时从建单UTC开始，离线也经过；本地时钟只用于测试，不能声称防修改时钟。

5. 商业化位置与节奏

位置B v1 规则失败与保护
通关/果篮自愿3倍玩家明确点击视频按钮；一天最多12次成功观看失败或取消仍可拿基础奖；仅有效完成回调补发差额，回调去重。
复活、免费道具保留已有入口，接公共广告接口；不加入买道具页与加奖共享展示互斥，不与结算或任务页叠弹；失败可正常重开。
自然插屏满足通关≥3且有效游玩≥150秒；每2次普通通关领取可产生一次机会还须共同冷却≥90秒、每天最多8次（展示前计数<8）；只在领取后进入下一关前，禁止水果点击中弹出。
激励后保护成功后30秒内不插屏，并跳过下一次自动广告机会同一节点最多请求一条；失败也不立刻补另一类型。
钱包/引导/任务无强制广告不把广告数加进订单条件；不因点击提现强制广告。

所有广告入口（含复活与道具）都遵守第1～2关不播放广告的保护；此时保留已有免费资源，不足时可正常重开。普通领取机会计数在领取成功后更新；曝光次数仅按去重后的SDK曝光回调更新；激励完成数按有效奖励回调更新。每个自然节点至多一次请求，失败或取消后本节点不重试。以上均是 B 建议参数，须配置化。广告SDK未接入时继续用明确的测试提供者；收入分析必须等两组接入相同生产广告能力后，另开实验版本。自动广告计次、展示次数和收入分别记录，不能用“请求成功”冒充曝光。

7. 两套保留及AB接入约定

  1. 保留A：原资源、配置、业务代码和原存档继续存在；A/B不是在同一个Prefab上互相覆盖。首次接入B前记录A实际发布构建与规则版本，当前未提交改动单独核实。
  2. 独立B：OrchardEarning/B/Panels/、OrchardEarning/B/OrchardBConfig、fruit-orchard-earning-b-v1.dat；大图按需加载。共享字体和基础图标可以，但B布局不写回A资源。
  3. 只分一次：老玩家固定A；实验新用户按实验ID与稳定安装/账号标识分50/50，第一次发业务事件前持久化。重启、断网和修改权重不改变已分组用户。无账号的重装视新安装，单独标识这一限制。
  4. 唯一路由：实际BeginRun / RecordTriple / RecordWin经当前方案适配器转发一次。两组服务不能同时监听发奖。弹窗队列和结算完成信号也只由当前组持有。
  5. 玩法可比：线上两组用相同关卡、难度、操作与广告SDK版本；商业化余额、任务、引导、订单独立。QA切换仅限安全入口，使用各组独立的整份玩法快照，不把同一已完成局再送另一组。
  6. 固定规则：订单保存金额、版本、建单时刻、门槛和计数起点。远端只影响新订单；紧急关B时停止新分配，已有B存档保留，不静默改A。
  7. Unity实现：结构、颜色、字号、资源路径用Prefab/ScriptableObject；业务控制显示和绑定标准Button。无反射、无枚举字符串存档key、无Editor专用核心逻辑。

8. 实验指标、阶段和验收

第一阶段：内部流程验证；当前模拟广告数据只衡量点击与测试流程。第二阶段：接同一广告提供者、稳定两组后，以新实验ID对新玩家分组。首次先做小流量故障观察，再扩大；不在中途改现金数值、广告强度和任务门槛。

类别指标与口径
主要体验指标按首次分组人数为分母：首局/前5关完成率、24～48小时回访率、7日回访率；退出/卡死率。
商业化指标正式SDK阶段：D0/D7广告收入÷分组用户，RV有效曝光/完成率，插屏曝光/用户；按系统、渠道、版本分层。
B漏斗五关汇总曝光→查看申请→确认成功→三项分别完成→测试完成；因等待48h，完成率使用成熟至少72h的人群，报告截止时仍等待人数。
比较限制A后段没有同定义的完成终点，不用A/B提现完成率直接判胜；比较共同入口与留存，B单独报告任务完整性。
护栏水果可点击、单一结算、冷启动直接入关、不重弹旧结算、首屏遮挡、崩溃/ANR、广告失败后的基础奖励。
事件维度experiment_id / variant_id / rules_version / config_hash / install_cohort / session_id / run_id / reward_id / order_id / ad_request_id；测试与真实SDK数据分流。
统计约定按首次分组分析，不按后来是否点过钱包重分组。根据实际基线与希望检测的提升计算样本量；观察成熟D7人群及区间，不用每天提前挑胜者。

必要验收：重复点击/重复广告回调仅发一次；后台恢复和重启不重复建单；余额冻结、退回、完成互斥；每日刷新不双领；长文本不溢出；已有活跃单时五关奖励照发；最后一组不出幸运弹窗；测试完成不再新增条件；A资源、存档、现有流程回归一致。计时用可注入时钟测试同一运行逻辑，不能做Editor专用捷径。
